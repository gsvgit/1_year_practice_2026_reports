\section{Постановка задачи}

Работа выполняется в рамках исследования открытых GPGPU (General-Purpose Graphics Processing Unit~--- графических процессоров общего назначения) архитектур на базе набора команд RISC-V (Reduced Instruction Set Computer~V)\footnote{The RISC-V Instruction Set Manual. URL: \url{https://riscv.org/technical/specifications/} (дата обращения: \DTMdate{2026-05-10}).}. Объектом исследования выступает проект Vortex\footnote{Vortex GPGPU Project. URL: \url{https://github.com/vortexgpgpu/vortex} (дата обращения: \DTMdate{2026-05-10}).}~--- открытая реализация GPGPU, предоставляющая полный RTL-код (Register Transfer Level~--- уровень регистровых передач), что позволяет проводить детальный архитектурный анализ в отличие от закрытых решений NVIDIA.

\textbf{Целью работы является} проведение параметрического анализа конфигураций Vortex и оценка эффективности использования вычислительных ядер и кэш-иерархии с точки зрения производительности и потребления ресурсов FPGA (Field-Programmable Gate Array~--- программируемая логическая интегральная схема).

Для достижения цели были поставлены следующие задачи:
\begin{enumerate}
    \item Разработать сценарий автоматизации для проведения параметрических экспериментов и извлечения метрик;
    \item Провести эксперименты сильного масштабирования, масштабирования кэша и слабого масштабирования для анализа масштабируемости;
    \item Выполнить аналитическую оценку потребления ресурсов FPGA (в частности, блоков BRAM~--- Block RAM, блочной памяти) для исследованных конфигураций.
\end{enumerate}

Результаты работы необходимы для понимания архитектурных особенностей Vortex при выполнении задач, интенсивно работающих с памятью. Для исследователей архитектур и разработчиков это полезно тем, что позволяет избежать неэффективного использования ресурсов FPGA (BRAM) при конфигурации GPU для задач с потоковым характером доступа к памяти. В выполнении работы заинтересована кафедра для формирования рекомендаций по настройке экземпляров Vortex под различные классы задач.

\section{Описание предлагаемого решения}

В качестве среды моделирования используется программный симулятор \texttt{simx}\footnote{Software simulator simx of the Vortex project. URL: \url{https://github.com/vortexgpgpu/vortex/tree/master/sim/simx} (дата обращения: \DTMdate{2026-05-10}).}, входящий в состав проекта Vortex. Он выбран по причине высокой скорости работы по сравнению с полной RTL-симуляцией и отсутствия необходимости проведения синтеза для FPGA на ранних этапах оценки тенденций масштабирования. Важно отметить, что \texttt{simx} не является строго потактово точным, однако позволяет корректно оценивать относительные изменения производительности между конфигурациями.

Для достижения цели был предложен подход, основанный на автоматизированном тестировании модели Vortex с последующим извлечением метрик. Варьировались два главных архитектурных параметра: количество вычислительных ядер и размер кэш-иерархии. Эксперименты проводились на двух задачах с различной арифметической интенсивностью:
\begin{itemize}
    \item \texttt{vecadd} (векторное сложение)~--- задача, чувствительная к пропускной способности памяти, с нулевой временной локальностью данных;
    \item \texttt{sgemm} (умножение матриц одинарной точности)~--- задача с высокой вычислительной нагрузкой и высокой временной локальностью.
\end{itemize}

Базовая конфигурация ядра включает 4 варпа (минимальной единицы планирования потоков в SIMD-архитектуре, Single Instruction Multiple Data~--- архитектуре с одним потоком команд и множеством потоков данных) и стандартный конвейер Vortex. Реализация решения осуществлялась с использованием скриптов сборки Bash\footnote{Bash~--- командная оболочка UNIX-подобных систем. URL: \url{https://www.gnu.org/software/bash/} (дата обращения: \DTMdate{2026-05-10}).}, языка Python\footnote{Python~--- высокоуровневый язык программирования. URL: \url{https://www.python.org/} (дата обращения: \DTMdate{2026-05-10}).} для автоматизированного извлечения метрик из логов и визуализации данных (библиотеки pandas\footnote{pandas~--- библиотека Python для обработки и анализа данных. URL: \url{https://pandas.pydata.org/} (дата обращения: \DTMdate{2026-05-10}).} и matplotlib\footnote{matplotlib~--- библиотека Python для построения графиков. URL: \url{https://matplotlib.org/} (дата обращения: \DTMdate{2026-05-10}).}), а также аналитической модели оценки ресурсов FPGA от Xilinx\footnote{Xilinx (ныне входит в состав AMD)~--- производитель FPGA. URL: \url{https://www.xilinx.com/} (дата обращения: \DTMdate{2026-05-10})}.. Для обеспечения воспроизводимости результатов был разработан сценарий автоматизации, позволяющий запускать серию экспериментов одной командой.

\section{Эксперименты}

Экспериментальное исследование проводилось в три этапа: сильное масштабирование (фиксированный объём данных, рост числа ядер), масштабирование кэша (фиксированное число ядер, рост объёма кэша) и слабое масштабирование (пропорциональный рост данных и числа ядер). 

Эксперименты проводились 4 мая 2026 года на ноутбуке Huawei MateBook 14 2024 под управлением операционной системы Ubuntu 24.04.4. Машина оснащена процессором Intel Core Ultra 5 125H (архитектура Meteor Lake, x86\_64) и 16~ГБ оперативной памяти LPDDR5X. Использовалась версия проекта Vortex, актуальная на дату проведения экспериментов. Симулятор \texttt{simx} запускался в стандартном режиме без дополнительных флагов оптимизации.

В качестве основной метрики производительности используется количество тактов симулятора. Эта метрика выбрана потому, что она непосредственно отражает время выполнения задачи на архитектуре и позволяет однозначно сравнивать различные конфигурации между собой. Модель симулятора является детерминированной, поэтому результаты запусков воспроизводимы без статистического разброса. Для оценки ресурсов FPGA применялась аналитическая модель, где за единицу измерения принят стандартный блок блочной памяти Xilinx BRAM36 (округлённо 4~КБ). Аналитическая модель (а не реальный синтез) выбрана по причине отсутствия доступа к инструментам синтеза для целевой FPGA на этапе данного исследования; такая оценка даёт корректное представление о порядке величин и относительной стоимости конфигураций.

На основе сформулированных задач были выделены следующие исследовательские вопросы:
\begin{itemize}
    \item \textbf{RQ1:} Как соотносится эффективность масштабирования ядер для задач с различной арифметической интенсивностью (\texttt{vecadd} против \texttt{sgemm})?
    \item \textbf{RQ2:} Как влияет увеличение объёма кэш-иерархии (L2/L3) на производительность задач с потоковым характером доступа к памяти?
\end{itemize}

\textbf{Результаты сильного масштабирования:}
Увеличение числа ядер с~1 до~4 на задаче \texttt{vecadd} (16~тыс. элементов) дало ускорение всего в~$1,06$~раза относительно конфигурации с одним ядром. Показатель IPC (Instructions Per Cycle~--- количество инструкций, выполняемых за один такт) каждого ядра упал с~$0,795$ до~$0,219$, то~есть в~$3,6$~раза. Как видно на Рисунке~\ref{fig:vecadd_strong}, реальное ускорение далеко от идеального линейного масштабирования. Падение IPC свидетельствует о том, что ядра значительную часть времени простаивают в ожидании данных. На графике ниже по оси абсцисс отложено количество вычислительных ядер, а по оси ординат~--- ускорение выполнения задачи в количестве раз относительно конфигурации с одним ядром.

\begin{figure}[H]

    \caption{Сильное масштабирование для задачи \texttt{vecadd}}
    \label{fig:vecadd_strong}
\end{figure}

Для сравнения, задача \texttt{sgemm} на~2~ядрах показала ускорение в~$1,33$~раза, а~на~4~ядрах~--- в~$1,51$~раза относительно конфигурации с одним ядром (Рисунок~\ref{fig:sgemm_strong}). Хотя \texttt{sgemm} имеет высокую арифметическую интенсивность, ускорение не достигает идеальных $4$~раз. Это указывает на то, что объёмов кэша L1 (16~КБ) недостаточно для полного покрытия рабочих множеств матриц, и ядра сталкиваются с задержками при обращении к подсистеме памяти. На соответствующем графике по горизонтальной оси показано количество ядер, а по вертикальной~--- ускорение работы в количестве раз относительно одноядерной конфигурации.

\textbf{Результаты масштабирования кэша:}
Включение L2-кэша (1~МБ) для одного ядра на задаче \texttt{vecadd} дало +15~\% ускорения, однако на~4~ядрах привело к \textbf{снижению} производительности. Добавление L3-кэша (2~МБ) не дало никакого прироста (Рисунок~\ref{fig:cache_impact}). 

Это объясняется характером доступа к памяти: \texttt{vecadd} обладает идеальной пространственной локальностью (последовательный обход массива), но полностью лишено временной локальности (данные читаются один раз и не переиспользуются). Следовательно, потоковые данные просто заполняют большие объёмы L2/L3, не принося выигрыша от попаданий в кэш. Поскольку кэш L1 приватен для каждого ядра, разделяемый L2 выступает первой точкой сериализации доступа, где на множестве ядер возникает конкуренция за арбитраж и конфликты по наборам кэша из-за выравнивания адресов, что и приводит к снижению производительности. На Рисунке~\ref{fig:cache_impact} по горизонтальной оси отложены исследованные конфигурации, сочетающие число ядер (1C и 4C) и тип кэш-иерархии (базовый уровень без L2 обозначен как «No L2», конфигурации с кэшем~--- как «L2» и «L2+L3»), а по вертикальной оси~--- время выполнения задачи в тактах.

\begin{figure}[H]

    \caption{Влияние иерархии кэшей на время выполнения (в тактах) для 1 и 4 ядер}
    \label{fig:cache_impact}
\end{figure}

\textbf{Результаты слабого масштабирования (задача \texttt{vecadd}):}
При пропорциональном увеличении объёма данных с ростом числа ядер (16~тыс./1~ядро, 32~тыс./2~ядра, 64~тыс./4~ядра) время выполнения росло почти линейно: от~622~тыс. тактов для 1~ядра до~2,38~млн тактов для 4~ядер. В идеальной архитектуре при слабом масштабировании время выполнения должно оставаться постоянным. Как видно на Рисунке~\ref{fig:weak_scaling}, наблюдается тенденция к росту времени выполнения при увеличении нагрузки. Аналогичные эксперименты для задачи \texttt{sgemm} показали схожую тенденцию. Данный результат указывает на то, что наблюдаемое ограничение масштабирования не зависит исключительно от арифметической интенсивности задачи и требует дополнительного исследования природы накладных расходов. На Рисунке~\ref{fig:weak_scaling} представлен полученный график зависимости. По горизонтальной оси отложено количество ядер совместно с сомасштабированным объёмом данных, а по вертикальной~--- время выполнения задачи в тактах. На график нанесены две линии: сплошная линия с маркерами, отображающая реальные зафиксированные показатели симулятора Vortex, и горизонтальная пунктирная линия, которая задаёт теоретическое идеальное время выполнения в условиях полной изолированности ядер и отсутствия конфликтов за общие ресурсы подсистемы памяти.

\textbf{Оценка ресурсов FPGA:}
В связи с отсутствием синтеза для целевой FPGA, оценка потребления ресурсов выполнена аналитически на основе объёмов памяти конфигураций. Базовая конфигурация (1~ядро, 16~КБ кэша инструкций L1 + 16~КБ кэша данных L1) требует 8~блоков~BRAM. Конфигурация с 4~ядрами, L2 (1~МБ) и L3 (2~МБ) требует: $4 \times 8$~блоков~BRAM (L1) + 256~блоков~BRAM (L2) + 512~блоков~BRAM (L3) = 800~блоков~BRAM. Эффективность использования ресурсов в данной работе оценивается как отношение ускорения выполнения задачи (относительно одноядерной конфигурации) к количеству использованных блоков~BRAM. Для базовой конфигурации (1~ядро, 8~блоков~BRAM) ускорение равно $1{,}00$, эффективность составляет $1{,}00 / 8 = 0{,}125$. Для конфигурации с 4~ядрами, L2 и L3 (800~блоков~BRAM) ускорение равно $1{,}06$, эффективность составляет $1{,}06 / 800 \approx 0{,}0013$. Таким образом, данная конфигурация не обеспечивает прироста скорости для задач с потоковым доступом, а эффективность использования ресурсов FPGA при инвестициях в кэш-иерархию без учёта паттернов доступа снижается более чем в 90~раз. 

\textbf{Угрозы нарушения корректности:}
При проведении экспериментов были выявлены следующие факторы, влияющие на валидность результатов:
\begin{itemize}
    \item Симулятор \texttt{simx} не является строго потактово точным, что может вносить искажения в абсолютные значения метрик, но сохраняет корректность относительных тенденций;
    \item Использование заданных по умолчанию параметров запуска ядер OpenCL (Open Computing Language~--- открытого языка вычислений на гетерогенных системах) без ручной настройки размера рабочих групп может занижать производительность из-за отсутствия объединения запросов к памяти.
\end{itemize}

\section{Заключение}

В ходе выполнения работы получены следующие результаты:
\begin{itemize}
    \item Разработан сценарий автоматизации (Bash + Python) для извлечения метрик из логов и визуализации результатов, обеспечивающий воспроизводимость исследования;
    \item Выявлено ограничение масштабирования для задач, чувствительных к пропускной способности памяти (\texttt{vecadd}, ускорение в~$1,05$~раза на~4~ядрах относительно конфигурации с одним ядром), на фоне более эффективного ускорения задач с высокой арифметической интенсивностью (\texttt{sgemm}, в~$1,51$~раза);
    \item Показано, что при выбранных параметрах запуска увеличение объёма кэш-иерархии (L2/L3) не приводит к росту производительности для задач с нулевой временной локальностью из-за заполнения кэша и конкуренции за порты;
    \item Выполнена аналитическая оценка потребления ресурсов FPGA (BRAM), показавшая снижение эффективности использования ресурсов в конфигурациях с большими кэшами для задач с линейным доступом к данным.
\end{itemize}
