\section{Введение}

Работа выполняется в рамках исследования открытых GPGPU (General-Purpose Graphics Processing Unit~--- графических процессоров общего назначения) архитектур на базе набора команд RISC-V (Reduced Instruction Set Computer~V (пятое поколение))\footnote{The RISC-V Instruction Set Manual. URL: \url{https://riscv.org/technical/specifications/} (дата обращения: \DTMdate{2026-05-10}).}. Объектом исследования выступает проект Vortex\footnote{Vortex GPGPU Project. URL: \url{https://github.com/vortexgpgpu/vortex} (дата обращения: \DTMdate{2026-05-10}).}~--- открытая реализация GPGPU, предоставляющая полный RTL-код (Register Transfer Level~--- уровень регистровых передач), что позволяет проводить детальный архитектурный анализ в отличие от закрытых решений NVIDIA.

 \section{Постановка задачи}

\textbf{Целью работы является} проведение параметрического анализа конфигураций Vortex.

Для достижения цели были поставлены следующие задачи:
\begin{enumerate}
    \item Разработать сценарий автоматизации\footnote{Репозиторий на Github с исходным кодом сценария автоматизации. URL: \url{https://github.com/Makuhin-Egor/Vortex-experiments-styding-practice} (дата обращения: \DTMdate{2026-05-10}).} для проведения параметрических экспериментов и извлечения метрик.
    \item Провести эксперименты сильного масштабирования (зависимость ускорения от количества вычислителей при фиксированном размере задачи).
\end{enumerate}

Результаты работы необходимы для понимания архитектурных особенностей Vortex. Для исследователей архитектур и разработчиков это полезно тем, что позволяет избежать неэффективного использования ресурсов FPGA (Field-Programmable Gate Array~--- программируемая логическая интегральная схема) при конфигурации GPU для задач ограниченной вычислительной мощности и ограниченной пропускной способности памяти. В выполнении работы заинтересована кафедра для формирования рекомендаций по настройке экземпляров Vortex под различные классы задач.

\section{Описание предлагаемого решения}

В качестве среды моделирования используется программный симулятор \texttt{simx}\footnote{Software simulator simx of the Vortex project. URL: \url{https://github.com/vortexgpgpu/vortex/tree/master/sim/simx} (дата обращения: \DTMdate{2026-05-10}).}, входящий в состав проекта Vortex. Он выбран по причине высокой скорости работы по сравнению с полной RTL-симуляцией и отсутствия необходимости проведения синтеза для FPGA на ранних этапах оценки тенденций масштабирования. Важно отметить, что \texttt{simx} не является строго потактово точным, однако позволяет корректно оценивать относительные изменения производительности между конфигурациями.

Для достижения цели был предложен подход, основанный на автоматизированном тестировании модели Vortex с последующим извлечением метрик. Варьировались следующие параметры: количество вычислительных ядер, количество кластеров (групп вычислительных ядер, объединённых общей памятью или разделяющих некоторые ресурсы) (количество кластеров изменялось с целью увеличить максимальное количество доступных ядер (данный параметр принимал значения $1 \dots 4$)) и размер входных данных. Остальные параметры были в состоянии по умолчанию. Эксперименты проводились на двух задачах с различной арифметической интенсивностью (отношением числа арифметических операций к объёму переданных данных):
\begin{itemize}
    \item \texttt{vecadd} (векторное сложение)~--- задача, чувствительная к пропускной способности памяти, с нулевой временной локальностью данных (повторным обращением к одним и тем же данным в течение короткого времени);
    \item \texttt{sgemm} (умножение матриц одинарной точности)~--- задача с высокой вычислительной нагрузкой и высокой временной локальностью.механизм, распределяющий варпы по ядрам
\end{itemize}

Количество ядер ($1 \dots 64$): Использование степеней двойки обусловлено аппаратной архитектурой Vortex и аппаратным планировщиком варпов (механизм, распределяющий варпы по ядрам). Это исключает дисбаланс при распределении блоков потоков (группа потоков, выполняющихся на одном ядре) по ядрам. 

Размеры \texttt{vecadd} ($16\,384 \dots 65\,536$): Подобраны для демонстрации того, как при слабой вычислительной нагрузке рост производительности быстро упирается в скорость работы шины памяти независимо от объема вектора.

Размеры \texttt{sgemm} ($128 \dots 512$): Выбраны, чтобы определить минимальный объем вычислений, необходимый для эффективной загрузки большого числа ядер.

Базовая конфигурация ядра включает 4~варпа (минимальной единицы планирования потоков в SIMD-архитектуре, Single Instruction Multiple Data~--- архитектуре с одним потоком команд и множеством потоков данных) и стандартный конвейер Vortex. В качестве программного стека для разработки и запуска исследуемых параллельных приложений используется OpenCL (Open Computing Language~--- открытый язык вычислений на гетерогенных системах)\footnote{OpenCL~--- открытый стандарт параллельного программирования гетерогенных систем. URL: \url{https://www.khronos.org/opencl/} (дата обращения: \DTMdate{2026-05-10}).}. Написанные на OpenCL вычислительные ядра компилируются под архитектуру команд Vortex, а программный симулятор \texttt{simx} эмулирует их выполнение.

Реализация решения осуществлялась с использованием скриптов сборки Bash\footnote{Bash~--- командная оболочка UNIX-подобных систем. URL: \url{https://www.gnu.org/software/bash/} (дата обращения: \DTMdate{2026-05-10}).}, языка Python\footnote{Python~--- высокоуровневый язык программирования. URL: \url{https://www.python.org/} (дата обращения: \DTMdate{2026-05-10}).} для автоматизированного извлечения метрик из логов и визуализации данных (библиотеки pandas\footnote{pandas~--- библиотека Python для обработки и анализа данных. URL: \url{https://pandas.pydata.org/} (дата обращения: \DTMdate{2026-05-10}).} и matplotlib\footnote{matplotlib~--- библиотека Python для построения графиков. URL: \url{https://matplotlib.org/} (дата обращения: \DTMdate{2026-05-10}).}). Для обеспечения воспроизводимости результатов был разработан сценарий автоматизации, позволяющий запускать серию экспериментов одной командой.

\section{Эксперименты} 

Эксперименты проводились на ноутбуке Huawei MateBook 14 2024 под управлением операционной системы Ubuntu 24.04.4. Машина оснащена процессором Intel Core Ultra 5 125H (архитектура Meteor Lake, x86\_64) и 16~ГБ оперативной памяти LPDDR5X. Использовалась соответствующая коммиту 9540c33 версия проекта Vortex. Симулятор \texttt{simx} запускался в стандартном режиме без дополнительных флагов оптимизации. Использовалася версия Python 3.14.4,  а также библиотек pandas 3.0.2 и matplotlib 3.10.9.

В качестве основной метрики производительности используется количество тактов симулятора. Эта метрика выбрана потому, что она непосредственно отражает время выполнения задачи на архитектуре и позволяет однозначно сравнивать различные конфигурации между собой. Модель симулятора является детерминированной, поэтому результаты запусков воспроизводимы без статистического разброса.

На основе сформулированных задач были выделены следующие исследовательские вопросы (RQ~--- Research Questions):
\begin{itemize}
    \item \textbf{RQ1:} Какая из задач (\texttt{vecadd} или \texttt{sgemm}) масштабируется ближе к линейной зависимости при увеличении количества вычислительных ядер?
    \item \textbf{RQ2:} Влияет ли увеличение количества входных данных на масштабируемость задач \texttt{vecadd} и \texttt{sgemm}?  
\end{itemize}

\textbf{Анализ задачи \texttt{sgemm} с матрицей размерностью 128:}
Для матрицы $128\times128$ график (рис.~\ref{fig:strong_sgemm_128}) демонстрирует близкое к идеальному линейное масштабирование до 8~ядер ($7.9\times$). На 16~ядрах ускорение достигает $14.2\times$, на 32~ядрах пика в $16.2\times$, после чего на 64~ядрах происходит небольшой спад до $15.7\times$. Причина в том, что sgemm~--- вычислительно интенсивный алгоритм, где данные активно переиспользуются в регистровом файле и L1-кэше. Однако при размере $128\times128$ общий объём вычислений относительно мал ($128^3$ операций). На 64~ядрах объем работы на одно ядро снижается настолько, что накладные расходы на барьерную синхронизацию и взаимодействие между кластерами преобладают над полезной работой, вызывая деградацию ускорения (отрицательное масштабирование).

\textbf{Анализ задачи \texttt{sgemm} с матрицей размерностью 256:}
При размере матрицы $256\times256$ линейный рост ускорения на графике (рис.~\ref{fig:strong_sgemm_256}) сохраняется вплоть до 16~ядер ($15.5\times$), а максимум достигается на 32~ядрах ($19.2\times$). На 64~ядрах наблюдается спад до $16.7\times$. Рост объема данных в 8~раз по сравнению с матрицей размера $128\times128$ позволил существенно продлить область идеального масштабирования (до 16~ядер ускорение идет практически по пунктирной линии идеала). Падение на 64~ядрах связано с той же причиной, что и в предыдущем эксперименте.

\textbf{Анализ задачи \texttt{sgemm} с матрицей размерностью 512:}
Для матрицы $512\times512$ на соответствующем графике (рис.~\ref{fig:strong_sgemm_512}) наблюдается наилучшая масштабируемость: идеальное линейное ускорение выдерживается до 16~ядер ($16.0\times$), а абсолютный максимум достигается на 32~ядрах ($22.6\times$), с незначительным понижением на 64~ядрах ($21.4\times$). Большой размер матрицы обеспечивает высокую вычислительную загрузку арифметических блоков каждого ядра. Вплоть до 32~ядер система использует параллелизм без существенных простоев, и лишь на 64~ядрах сказываются архитектурные ограничения по масштабированию межкластерного взаимодействия.

\textbf{Вывод из экспериментов задачи \texttt{sgemm}:}
Сравнение трёх графиков масштабирования задачи \texttt{sgemm} чётко иллюстрирует главное правило сильного масштабирования для вычислительно ёмких задач: чем больше размер входной задачи, тем дольше сохраняется линейное ускорение и тем выше достигаемый пик производительности. Благодаря высокой арифметической плотности, задача почти линейно масштабируется на малом и среднем количестве ядер (1~--~16). Ограничение роста после 32~ядер на всех трех графиках обусловлено проявлением закона Амдала\footnote{Amdahl's law~--- закон, иллюстрирующий ограничение роста производительности вычислительной системы с увеличением количества вычислителей. URL: \url{https://en.wikipedia.org/wiki/Amdahls_law} (дата обращения: \DTMdate{2026-05-10}).}.

По горизонтальной оси отложено количество ядер, по вертикальной~--- ускорение относительно конфигурации с одним ядром, для которой оно равно $1.0\times$. Ускорение является безразмерной величиной. \textbf{Анализ задачи \texttt{vecadd} с векторами длины 16384:}
При размере вектора в $16\,384$ элемента (рис.~\ref{fig:strong_vecadd_16384}) ускорение растёт почти линейно лишь до 4~ядер (ускорение $3.5\times$), после чего кривая становится практически горизонтальной и почти не растёт с 8 до 64~ядер ($3.6\times \dots 4.0\times$). Главная причина заключается в том, что задача vecadd строго ограничена пропускной способностью памяти. При 4~ядрах шина памяти практически полностью насыщается запросами. Дальнейшее увеличение количества ядер не повышает суммарный поток данных.

\textbf{Анализ задачи \texttt{vecadd} с векторами длины 32768:}
Для объёма в $32\,768$ элементов (рис.~\ref{fig:strong_vecadd_32768}) наблюдается аналогичный характер масштабирования: до 4~ядер ускорение составляет $2.8\times$, а затем становится почти горизонтальной в диапазоне $3.1\times \dots 3.6\times$ на 64~ядрах. Увеличение объема данных вдвое по сравнению с прошлым тестом не приводит к принципиальному улучшению масштабируемости. Так как каждый элемент вектора запрашивается из памяти единожды без повторного использования, кэш-память не может скомпенсировать недостаток пропускной способности памяти.

\textbf{Анализ задачи \texttt{vecadd} с векторами длины 65536:}
На графике с наибольшими векторами ($65\,536$ элементов) (рис.~\ref{fig:strong_vecadd_65536}) кривая показывает начальный прирост на 2~--~4~ядрах ($2.8\times$), после чего замедляется и плавно доходит до $3.7\times$ на 64~ядрах. При столь большом векторе шина памяти загружена полностью уже на младших конфигурациях.

\textbf{Вывод из экспериментов задачи \texttt{vecadd}:}
Сравнение трёх графиков задачи \texttt{vecadd} показывает практически идентичный профиль сильного масштабирования: во всех случаях кривая сильно отклоняется от идеального линейного ускорения и становится практически горизонтальной на уровне $3.5\times \dots 4.0\times$. Различие в размерах почти не меняет итоговый предел масштабирования. Незначительно более высокий относительный показатель на 4~ядрах для размерности $16\,384$ объясняется тем, что меньший объём вектора лучше помещается в емкость кэшей ядер и системы кластеров в целом.

\textbf{Угрозы нарушения корректности:}
При проведении экспериментов были выявлены следующие факторы, влияющие на валидность результатов:
\begin{itemize}
    \item Симулятор \texttt{simx} не является строго потактово точным, что может вносить искажения в абсолютные значения метрик, но сохраняет корректность относительных тенденций.
    \item Использование заданных по умолчанию параметров запуска ядер OpenCL без ручной настройки размера рабочих групп может занижать производительность из-за отсутствия объединения запросов к памяти.
\end{itemize}

\section{Заключение}
